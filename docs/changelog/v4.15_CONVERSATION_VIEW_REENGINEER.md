# v4.15 — Conversation view re-engineering

## Summary

The Conversations tab is rebuilt so a logical conversation shows as **one instance** rendered from the most-complete request's full `messages[]` (a real Copilot-style system/user/assistant/tool thread), instead of stitching one user+assistant block per HTTP request from `prompt_text`/`response_text` (which showed a 19-message request as just System + last Tool Result + Assistant). Grouping no longer relies on the brittle fingerprint chaining; content and live streaming load only when a conversation is opened. Request History is unchanged (still per-request for debugging).

## What changed

- **New grouping key (`conversation_key`).** Computed at enqueue:
  - If the client sends a conversation-id header → `cid:{ip}:{id}`. The header list is prioritized and env-configurable (`CONVERSATION_ID_HEADERS`); defaults cover common clients (`X-Conversation-Id`, `X-OpenWebUI-Chat-Id`, `x-session-key`, `X-Session-Id`, `X-Thread-Id`, `X-Chat-Id`, `Conversation-Id`).
  - Otherwise a **head-key** → `hk:{ip}:{model}:{sha16(system + first user message)}`. This survives the tool-result reformatting that broke fingerprint chaining. A summarization that rewrites the head starts a new conversation (accepted trade-off).
- **Render from the canonical request.** `GET /proxy/conversation_thread?conversation_key=…` groups a conversation's requests, splits them into **segments** at compaction boundaries (a drop in message count), picks each segment's canonical (max `message_count`, tie-break latest), and returns only the canonical bodies' `messages[]` + that turn's final assistant response/thinking/tool_calls. Growing-prefix turns dedupe to one instance; segments get a "context compacted" divider.
- **Subscribe-on-open live model.** The `/live` WebSocket now streams chunk **content only to connections subscribed to the open conversation's `conversation_key`**. Lightweight lifecycle events (`request_started`/`queued`/`processing`/`completed`) still broadcast to all (list badges only, no content). On connect the broadcaster sends no content snapshot; a snapshot is sent when the client sends `{"type":"subscribe","conversation_key":…}`. This keeps data transfer minimal while browsing the list.
- **No auto-open.** New conversations no longer auto-open on the Conversations tab; opening one subscribes + fetches its thread; closing/switching unsubscribes.
- **Untruncated request bodies.** `request_body` is stored in full by default so ~1M-token histories render intact. `MAX_REQUEST_BODY_BYTES` (0/unset = no limit) is available as a safety valve; when a body is capped, the thread shows a "history unavailable" note for that segment.
- **Fingerprint chaining + diagnostics removed.** Enqueue no longer computes incoming/outgoing fingerprints or does the chaining lookup; `session_id` remains a unique per-request id (legacy grouping fallback + live correlation). `GET /proxy/conversation_diagnostics` and the dashboard "Chain diagnostics" panel are removed. The v4.14 fingerprint columns are left in place but dormant (SQLite column drops are destructive).

## Migration

Three nullable columns are added to `request_logs` — `conversation_id`, `conversation_key` (indexed via `ix_conversation_key`), `message_count`. Applied automatically on startup via `DatabaseConnection._add_missing_columns()`; a parity `migrate_to_v6()` is available in `scripts/migrate_db.py` for manual runs (`python scripts/migrate_db.py migrate`). All columns are nullable, so existing rows are unaffected (older rows fall back to `session_id` grouping and show `message_count` 0 until re-observed).

## Files

- `src/database.py` — new columns + `ix_conversation_key` index, runtime auto-migration, fallback-recovery mapping
- `src/data_access.py` — `log_request` accepts/persists `conversation_id`/`conversation_key`/`message_count` (create/update/fallback/return)
- `src/smart_proxy.py` — header detection + `compute_conversation_key`/`message_count` at enqueue; untruncated body (`MAX_REQUEST_BODY_BYTES`); `conversation_key` in `request_started` metadata; removed fingerprint computation + lookup
- `src/proxy_endpoints.py` — `conversation_sessions` groups by `conversation_key` (coalesced with `session_id`); new `GET /proxy/conversation_thread` + `select_conversation_segments`; `/live` WS parses subscribe/unsubscribe; removed `conversation_diagnostics`
- `src/live_broadcaster.py` — per-connection subscription state; `chunk` routed to subscribers; snapshot on subscribe
- `static/dashboard/app.js`, `index.html`, `app.css` — thread rendered from `conversation_thread` per segment; subscribe-on-open; removed Chain Diagnostics UI/CSS + dead helpers; cache-bust `app.css?v=12`, `app.js?v=14`
- `scripts/migrate_db.py` — `migrate_to_v6`
- `tests/` — header detection/key computation, segment/canonical selection, `log_request` persistence, `conversation_thread`/`conversation_sessions` endpoints, broadcaster subscription routing

## Trade-offs

- Head-key can merge two conversations that share the same system prompt + identical first user message from the same IP (prefer-merge; a persistent conversation-id header avoids this entirely).
- Untruncated bodies grow the DB; `conversation_thread` returns only canonical bodies to limit transfer, and `MAX_REQUEST_BODY_BYTES` caps if needed.
- v4.14 fingerprint/diagnostics are superseded; dormant columns remain (non-destructive).
