# v4.18 — Jev-style decision models (`POST /v1/systemone`)

## Summary

[Ollama 0.35 added support for Jev-style decision models](https://ollama.com/blog/ollama-now-supports-jev-style-decision-models)
(based on TypeSafe's Jev API): `POST /v1/systemone` takes a `state` object plus a set of named
`questions` and a local decision model answers them **all in one request**, with a probability per
option. Aimed at fast, cheap decisions — ticket triage, model routing, moderation — the announced
models are `nimble` (Bespoke Labs, 9B), `tev1` and `tev1:0.8b` (Together AI).

Before this change the endpoint fell through the catch-all forwarder in `src/ollama_endpoints.py`,
i.e. it was proxied **without queuing or logging**: no VRAM-aware scheduling (a cold `nimble` load
could stomp a loaded chat model with no queueing), no `request_logs` row, and no analytics — the
exact blind spot v4.12 removed for embeddings.

`/v1/systemone` is now a first-class queued + logged endpoint.

## The wire format

Request (from the announcement):

```json
{"model": "nimble",
 "state": {"ticket": "I was charged twice. Please refund the extra payment."},
 "questions": {
   "team":    {"type": "choice", "instructions": "Which team should handle this ticket?",
               "criteria": {"billing": "Payments and refunds", "technical": "Bugs and integrations",
                            "other": "None of the above"}},
   "refund":  {"type": "noul", "instructions": "Does the customer explicitly ask for a refund?"},
   "urgency": {"type": "score", "instructions": "How urgent is this ticket?",
               "criteria": ["Routine", "Soon", "Urgent"]}}}
```

Response — a single JSON document (**not** NDJSON):

```json
{"model": "nimble",
 "answers": {
   "team": {"type": "choice", "choice": "billing",
            "probabilities": {"billing": 0.985, "technical": 0.012, "other": 0.003}, "confidence": 0.922},
   "refund": {"type": "noul", "noul": 0.997},
   "urgency": {"type": "score", "score": 0.815, "legend": {"0": "Routine", "1": "Soon", "2": "Urgent"},
               "probabilities": {"0": 0.378, "1": 0.429, "2": 0.193}, "confidence": 0.046}},
 "usage": {"input_tokens": 841, "output_tokens": 4}}
```

## What changed

- **Route** (`src/ollama_endpoints.py`): explicit `POST /v1/systemone` → `enqueue_request(request, "v1/systemone")`, declared before the `/{path:path}` catch-all. Queued like chat, so the priority score (loaded / fits-in-parallel / swap) governs when the decision model is loaded, and it counts against `OLLAMA_MAX_PARALLEL`.
- **Prompt extraction** (`src/smart_proxy.py`): a body with `state`/`questions` renders into `prompt_text` via `format_decision_prompt()` — the flattened state (`ticket: I was charged twice. …`) plus a one-line question inventory (`[questions: team (choice: billing|technical|other), refund (noul), urgency (score: Routine|Soon|Urgent)]`). Both axes are bounded (`DECISION_STATE_VALUE_LIMIT`, `DECISION_QUESTION_PREVIEW_LIMIT`, ≤8 criteria per question); the untruncated specs stay in `request_body` for the raw-JSON view.
- **Response tap** (`src/stream_tap.py`): `render_decision_answers()` turns `answers` into one line — `team=billing (p=0.985) · refund=noul 0.997 · urgency=0.815` — which flows into `response_text` and the live broadcaster unchanged. Unknown answer types are kept (clipped) rather than dropped; `{"error": …}` still renders as `[Error] …`.
- **Token usage**: `usage.input_tokens` / `usage.output_tokens` map onto the existing `prompt_eval_count` / `eval_count` columns, so per-request token cost shows up in the dashboard **without a migration**.
- **Single-document safety**: the tap is line-oriented (NDJSON). If a server pretty-prints the JSON reply across lines, every line-wise parse fails, so `tee_stream` keeps a bounded copy (`DECISION_RAW_SAMPLE_LIMIT`) of decision responses and, when nothing was extracted, re-parses the whole body as one document. Bytes forwarded to the client are never touched, in either case.
- **Not a conversation**: decision requests carry no `messages`, so every call from an IP+model would hash to the same empty head-key — the v4.17 embedding bug, re-run. `DECISION_ENDPOINTS` joins `EMBEDDING_ENDPOINTS` in `NON_CONVERSATION_ENDPOINTS`; enqueue skips `conversation_key`/`message_count`/`conversation_id`, and the dashboard's Conversations queries (renamed `_exclude_non_conversations_filter()`) filter `endpoint = 'v1/systemone'` out — including historical rows. Request History and the analytics rollups still show everything.
- **Fallback label**: a decision response whose answers cannot be parsed logs `[Decision response — see raw JSON]` instead of `[HTTP 200]`.
- **Usage audit** (`scripts/model_usage_audit.py`): decision traffic is counted per model (`recent_decision_requests`) and never classified as probe noise.

## Migration

None. No schema change; the endpoint simply stops being invisible.

## Notes / trade-offs

- `proxy_endpoints.NON_CONVERSATION_ENDPOINTS` is a local copy (circular-import avoidance) and must stay in sync with `smart_proxy.NON_CONVERSATION_ENDPOINTS` — asserted by `tests/test_decision_models.py`.
- Decision requests share the queue with chat. They are latency-sensitive (≈91 ms per decision on M-series hardware), which the queue does not special-case: a request that must swap a large model out still scores 400/800 and waits its turn. If triage/routing loops become latency-critical here, the options are a dedicated concurrency lane or a priority offset for `v1/systemone` — deliberately out of scope for this change.
- The TypeSafe SDK works through the proxy unchanged (`TYPESAFE_BASE_URL=<proxy origin>`), since the proxy forwards the body and response bytes verbatim.
