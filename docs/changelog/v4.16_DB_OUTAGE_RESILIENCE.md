# v4.16 - DB Outage Resilience (DB-independent)

## Problem
Clicking "Simulate DB Down" (`POST /proxy/testing {"db_available": false}`) caused clients to receive
`500 Internal Server Error` on proxied requests, even though the proxy was designed to fall back to
file-based logging when the database is unavailable.

## Root cause
`DatabaseConnection.get_session()` raises immediately when the DB is unavailable (real outage or the
simulate flag). Most callers assigned `session` *inside* the `try` block and then referenced it in
their `except`/`finally` handlers. When `get_session()` raised before `session` was bound, the handler
itself threw `UnboundLocalError`, which masked the intended fallback and propagated out as a 500.

The client-facing path uses `RequestLogRepository.log_request` (and `update_request_log`), neither of
which had the `session = None` guard that `create_request_log` already had — which is why the existing
`test_fallback_logging.py` (exercising only `create_request_log`) passed while the real path failed.

Note: the simulate flag is DB-type-independent (it short-circuits `get_session()` regardless of SQLite
vs PostgreSQL), so this was never caused by switching backends. A genuine outage actually behaved more
gracefully because `get_session()` returns a lazy Session and the failure surfaced later at query time,
where `session` was bound.

## Changes
Centralized, backend-agnostic resilience keyed off `is_available()`:

- `src/database.py`
  - Added `DatabaseUnavailable` exception and a `DatabaseConnection.session_scope()` context manager
    that raises `DatabaseUnavailable` before yielding when the DB is down and guarantees safe teardown
    (rollback-on-error and close are both wrapped so teardown can never raise). `get_session()` kept for
    compatibility.
  - `AnalyticsQueryBuilder` query methods now guard `session` and return safe empties (`[]`) instead of
    raising; `build_home_analytics_from_rollups` / `build_histogram_series` return `None` when the DB is
    unavailable.
- `src/data_access.py`
  - `log_request`, `update_request_log`, `create_request_log` early-out to file logging when
    `is_available()` is false and never propagate (guarded `session`, guarded rollback/close, wrapped
    fallback write). The client request path can no longer 500 due to the DB.
  - Read getters (`get_request_log`, `get_request_logs_by_model`, `get_request_logs_by_ip`,
    `get_request_by_ip_and_outgoing_fingerprint`) degrade to `None`/`[]` instead of raising.
- `src/proxy_endpoints.py`
  - `query_db` and `conversation_sessions` return an empty page instead of a 500 during an outage;
    `conversation_thread` returns `503 Service Unavailable`. All three guard the session safely.
- `src/rollup_ops.py`, `src/smart_proxy.py`
  - Rollup upserts/purges and the log-retention task use `session_scope` / an availability check for
    consistency and to avoid future unbound-session errors.

## Tests
- Added `tests/test_db_resilience.py`:
  - `log_request` for a NEW request and for an UPDATE do not raise and write a fallback file while the
    DB is simulated down.
  - Read getters and analytics methods degrade gracefully (return `None`/`[]`).
  - After restoring the DB, fallback records recover and the fallback files are removed.
- Existing `test_database.py`, `test_fallback_logging.py`, `test_admin_dashboard.py`,
  `test_analytics.py`, `test_conversation_grouping.py`, `test_stale_sweeper.py`, `test_logging.py` pass.
  (`test_queue.py` is a live-network integration test and is not runnable offline.)
