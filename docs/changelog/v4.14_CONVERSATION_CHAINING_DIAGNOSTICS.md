# v4.14 — Conversation chaining diagnostics

## Summary

Observability for the content-based session chaining, so it is possible to determine from real traffic (e.g. GitHub Copilot agent runs) whether the proxy failed to link turns or the client sent divergent histories. No change to the matching algorithm itself.

- **Persisted matching signals:** Each request now stores `incoming_conversation_fingerprint` (hash of its message prefix), `session_matched_request_id` (the prior request it chained from, or NULL for a new session), and `prefix_message_count`. Previously only the outgoing fingerprint was persisted, so the match outcome was unrecoverable after the fact.
- **Diagnostics endpoint:** `GET /proxy/conversation_diagnostics` (admin) returns per-request signals for a filtered set (`ip_address`, `model`, `from_time`, `to_time`, `session_id`) ordered by time, plus a chain analysis that classifies each break:
  - `proxy_miss` — a prior request from the same IP produced an outgoing fingerprint equal to this request's incoming fingerprint, but the session was not linked (a proxy bug/race to investigate).
  - `client_divergence` — the request's prefix matches no prior completed response; the response includes the first divergent message (role + truncated content of expected vs actual), recomputed from stored `request_body`/`response_text`/`tool_calls_json` using the same normalization helpers as live chaining. Marked unavailable when `request_body` was truncated (256KB).
- **Debug log:** A `session_chain_decision` debug line is emitted at enqueue time (incoming fp, matched, matched_request_id, prefix_message_count, session_id) to correlate live splits during test runs.
- **Dashboard:** A "Chain diagnostics" button on the Conversations tab (reusing the Model/IP filters) renders a table of requests with break rows annotated `proxy_miss` / `client_divergence` and the divergence snippet.

## Migration

Three nullable columns are added to `request_logs` plus an `ix_ip_incoming_fp` index. Applied automatically on startup via `DatabaseConnection._add_missing_columns()`; a parity `migrate_to_v5()` is also available in `scripts/migrate_db.py` for manual runs. All columns are nullable, so existing rows are unaffected (their diagnostics fields are simply empty until re-observed).

## Files

- `src/database.py` — new columns, model index, runtime auto-migration, fallback-recovery mapping
- `src/data_access.py` — `log_request` accepts/persists the three fields (create/update/fallback/return), preserving queue-time values on completion updates
- `src/smart_proxy.py` — `enqueue_request` captures matched request id + prefix count, passes them to the queue-time log, and emits the `session_chain_decision` debug log
- `src/proxy_endpoints.py` — `GET /proxy/conversation_diagnostics` + recompute/divergence helpers
- `static/dashboard/index.html`, `app.js`, `app.css` — Chain diagnostics panel; cache-bust `app.css?v=11`, `app.js?v=13`
- `scripts/migrate_db.py` — `migrate_to_v5`
- `tests/test_database.py`, `tests/test_admin_dashboard.py` — field persistence + endpoint classification tests
