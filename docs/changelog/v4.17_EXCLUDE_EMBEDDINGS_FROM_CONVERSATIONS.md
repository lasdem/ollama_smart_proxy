# v4.17 — Exclude embeddings from the Conversations view

## Summary

Embedding requests were collapsing into a single bogus "conversation" — e.g. `qwen3-embedding:8b-fp16 · 0 msg · 5985 turns`. Embeddings carry an `input` field, not chat `messages`, and embedding clients do not send conversation-id headers, so `compute_conversation_key` hashed an empty head (`system + first user message` were both empty) and produced the **same** head-key `hk:{ip}:{model}:{const}` for every call from a given IP+model. All embedding calls therefore piled into one bucket, and opening it made `conversation_thread` load thousands of full request bodies to render a non-conversation.

Embeddings are now excluded from the Conversations view. They remain fully visible in Request History and in the analytics rollups (unchanged since v4.12), so nothing is lost — the `input` text is still stored in both `prompt_text` and the raw `request_body`.

## What changed

- **No grouping key for embeddings (forward-looking).** `enqueue_request` now short-circuits for the embedding endpoints: `conversation_key`, `message_count`, and `conversation_id` are set to `None` rather than running `compute_conversation_key` over empty messages. New helper `_is_embedding_path()` + `EMBEDDING_ENDPOINTS` (`api/embed`, `api/embeddings`, `v1/embeddings`) in `src/smart_proxy.py`.
- **Endpoint-based exclusion in both Conversations queries (covers history).** `conversation_sessions` (the list) and `conversation_thread` (the detail loader) now filter out rows whose `endpoint` is an embedding endpoint. This is the robust part: it also hides the ~6000 historical rows that already carry the constant head-key. Loading an embedding key via `conversation_thread` now returns 404.
- **NULL-safe filter.** The exclusion is `endpoint IS NULL OR lower(trim(endpoint)) NOT IN (...)`, so legacy rows written before the `endpoint` column existed (endpoint `NULL`) are still shown as conversations.

## Why endpoint (not model name)

Filtering by the exact `endpoint` column is precise and matches both old and new rows. A `model_name LIKE '%embed%'` heuristic would be fragile and backend-dependent.

## Migration

None. This only adds query filters and changes a key assignment at enqueue. Historical embedding rows stay in the DB (visible in Request History) and simply drop out of the Conversations view.

## Files

- `src/smart_proxy.py` — `EMBEDDING_ENDPOINTS` + `_is_embedding_path`; skip conversation key/count/id for embedding paths in `enqueue_request`
- `src/proxy_endpoints.py` — local `EMBEDDING_ENDPOINTS` + `_exclude_embeddings_filter()`; applied to `conversation_sessions` and `conversation_thread`
- `tests/test_conversation_grouping.py` — unit tests for `_is_embedding_path`
- `tests/test_admin_dashboard.py` — `test_embeddings_excluded_from_conversations` (embedding row absent from `conversation_sessions`, its key 404s in `conversation_thread`, legacy `endpoint IS NULL` chat row still visible)

## Trade-offs

- The `proxy_endpoints` copy of `EMBEDDING_ENDPOINTS` is kept local to avoid a circular import from `smart_proxy`; it must stay in sync with the canonical set in `smart_proxy`.
