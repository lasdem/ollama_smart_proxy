# v4.12 — Embedding usage logging

## Summary
Embedding requests were previously invisible to analytics: `/api/embed`, `/api/embeddings`, and `/v1/embeddings` fell through the catch-all forwarder in `src/ollama_endpoints.py`, which forwards to Ollama without logging or rolling up. As a result embedding models never appeared in `request_logs` or `analytics_daily_by_model`, making it impossible to tell whether they were used.

This change routes the embedding endpoints through the existing `enqueue_request` queue so each call is logged to `request_logs` and rolled up into `analytics_hourly_by_model` / `analytics_daily_by_model`, exactly like chat/generate requests.

## Motivation
While auditing which installed models could be pruned, all "never used" models turned out to be embedding models. That was an artifact of the logging path (embeddings bypassed logging), not evidence of zero usage. Adding logging closes that blind spot so future prune decisions are based on real data.

## Changes
- `src/ollama_endpoints.py`: added explicit `POST /api/embed`, `POST /api/embeddings`, and `POST /v1/embeddings` routes that call `_enqueue_request_func` with the endpoint path. They are declared before the `/{path:path}` catch-all so they take precedence.
- `src/smart_proxy.py` (`enqueue_request`): added extraction of the `input` field (used by `/api/embed` and `/v1/embeddings`) into `prompt_text`. Lists are stored as JSON; the full request body is still captured in `request_body` (truncated at 256KB).
- `src/smart_proxy.py` (`on_stream_done`): when an embedding response has no streamed text content and is not an error, `response_text` is logged as `[Embeddings response]` instead of `[HTTP 200]`.
- `tests/test_embeddings.py`: new tests for (1) route wiring — each embedding endpoint enqueues with its own path and does not shadow other paths; (2) rollup integration — an embedding request logged through the repository creates a `request_logs` row and increments `analytics_daily_by_model`.

## Behavioral notes
- Embeddings now share the priority queue with chat/generate and count against `OLLAMA_MAX_PARALLEL`. Because embedding models are tiny (~0.2-0.7 GB) and tracked by the VRAM monitor from `/api/ps` like any other model, they typically score as loaded (0) or fit-in-parallel (150); only a model's first-ever request in a process (before it has been observed loaded) is treated as an unknown swap (300).
- The response stream is passed through unchanged by `tee_stream` (embedding paths extract no text), so embedding clients receive the raw Ollama/OpenAI JSON intact.
